`mnemom agent` launches your coding-agent CLI (Claude Code today) with its
model traffic routed through the Mnemom gateway. Every session runs under a
**governed agent identity**, shows up in your traces, and can carry a sealed
per-session **goal contract** that the gateway grades each turn against and
re-anchors the agent when it drifts.

It is designed to be one command: install once, then `mnemom agent`.

## Install once

```bash
npm install -g @mnemom/mnemom
mnemom login
```

<Note>
Access to `mnemom agent` is still by invitation (see below). `mnemom login`
opens a browser sign-in (device-code fallback on headless machines); set `MNEMOM_API_KEY` instead for CI. The CLI
keeps itself up to date in the background. If the Mnemom API needs a newer CLI
than the one you run, the CLI stops. In an interactive terminal, with a plain
`npm install -g` install and auto-update on (the default), it updates itself and asks you to run the command
again. Otherwise (CI, scripts, piped output, or other installs) it prints the
upgrade command, `npm i -g @mnemom/mnemom@latest`, for you to run. See
[Updates](/gateway/cli#updates-mnemom-update).
</Note>

<Note>
You need a coding-agent CLI to launch. Install
[Claude Code](https://claude.com/claude-code) first (`claude` on your `PATH`), or
point at any install with `--cli <name|/full/path>`.
</Note>

## Redeem an invitation

Mnemom Agent is rolling out to an invited cohort. If you received an invitation,
redeem it once:

```bash
mnemom agent --invite <token>
```

That signs you in (or creates your Mnemom account), unlocks Mnemom Agent for
your organization, and credits your starter µ. `mnemom agent invite <token>` does
the same as a sub-verb.

Without an invitation, `mnemom agent` stops before launching anything. It says
Mnemom Agent isn't enabled for your organization yet and shows how to redeem an
invitation. Nothing is started or charged. To request an invitation, contact us
at [mnemom.ai/contact](https://www.mnemom.ai/contact). `mnemom agent doctor`
shows the same access check.

Mnemom staff (`@mnemom.ai` accounts) are enabled by default and skip this step.

## Run

```bash
cd your-project
mnemom agent
```

With no arguments in a terminal, `mnemom agent` asks for one thing and then
launches: a **session name**, which labels the session in your traces and in
`mnemom agent sessions`. Enter takes the current folder name.

Goal alignment is not prompted for. Pass `--goal` to turn it on: the gateway
seals your one-line goal as a contract and nudges the agent back when it drifts,
for a little µ per turn. Without `--goal` the session runs governed with goal
alignment off. Either way the launch prints `goal alignment: on` or `off`.

Skip the prompt when you already know what you want:

```bash
mnemom agent fix-auth                                    # named, no goal
mnemom agent fix-auth --goal "make login work on Safari" # named, goal on
```

Non-interactive runs (pipes, CI) never prompt; they need a session name.

Before Claude Code starts, `mnemom agent` makes sure the agent the session runs
as is claimed in your org (see [Your governed agent](#your-governed-agent)). It
never starts a session on an unclaimed agent.

Your first launch in a terminal can also ask two one-time questions:

- How Claude Code should sign in to Anthropic, when there is a choice. See
  [Sign-in options](/gateway/agent-sign-in).
- Whether to look at what Mnemom would have saved on your recent sessions. See
  [Savings estimates](/gateway/agent-savings).

## Permission prompts

By default, `mnemom agent` starts Claude Code with
`--dangerously-skip-permissions`, so Claude Code does not ask before it edits
files or runs commands. Claude Code calls this Bypass Permissions mode. The first
time, it shows a warning and asks you to accept it before the session starts.
Claude Code recommends this mode only in a sandboxed container or VM.

To keep Claude Code's permission prompts, pass `--no-yolo`:

```bash
mnemom agent fix-auth --no-yolo
```

`--no-yolo` applies to that launch only; there is no saved setting for it, so
pass it on every launch where you want the prompts. `mnemom agent --dry-run`
shows which mode a launch would use (`yolo: on` or `off`).

## Resume a session

Each `mnemom agent` launch starts a new Claude Code session, even when you reuse
a session name. To pick up where you left off, relaunch through `mnemom agent`
and pass Claude Code's resume flag after `--`:

```bash
mnemom agent fix-auth -- --continue             # the most recent session in this folder
mnemom agent fix-auth -- --resume <session-id>  # a specific session
```

When Claude Code exits normally, the last line `mnemom agent` prints is the command to resume
it, for example:

```text
Resume with: mnemom agent fix-auth -- --resume <session-id>  (keeps it governed; `claude --resume` runs outside Mnemom)
```

If you named an agent with `--agent`, the command includes it.
`mnemom agent show <name>` prints the same command.

<Warning>
Claude Code prints its own hint just above that line: `claude --resume <session-id>`.
Do not run that command: it reopens the conversation outside Mnemom, with no
governance, no µ billing and nothing in your traces. Use the `mnemom agent`
command instead.
</Warning>

The resumed session runs governed, like any other launch, and the conversation
carries on where it stopped. Resuming with `-- --resume <session-id>` or
`-- --continue` keeps that session's context profile unless you pass
`--context-profile` (CLI 0.17.12 and later; earlier versions keep it only on
`--resume <session-id>`). If the session has no recorded profile, or there is no
earlier session in this folder, your default profile applies (see
[Context profiles](#context-profiles)). A sealed goal does not carry over: pass
`--goal` again to seal one for the resumed session.

If you have turned on [implicit goal mode](#implicit-goal-mode-experimental),
relaunching an implicit session by the same name asks "Resume previous
session?". Answer yes to continue that session and its inferred goal. See
[Implicit goal mode](/gateway/implicit-goal-mode) for details.

## Implicit goal mode (experimental)

A sealed goal (`--goal`) is one way to turn on goal alignment. The other is
**implicit mode**: no statement to write up front — the gateway infers the goal
from your messages and revises it as you steer. Guardrail ceilings
(`--max-turns`, `--budget`, `--stall`) still apply.

Implicit mode is an **experimental, opt-in feature**. It is never on by
default, on any cell, including cells where the gateway supports it. It runs
only after you opt in. Experimental features may change or be removed in any
release, with no deprecation period.

To opt in, turn on the experimental feature:

```bash
mnemom experimental enable implicit   # opt in (stored in ~/.mnemom/config.json)
mnemom experimental list              # see every experimental feature and whether it is on
```

Once you have opted in, a launch with no `--goal` runs in implicit mode:

```bash
mnemom agent fix-auth                 # goal alignment on, implicit, nothing sealed
mnemom agent fix-auth --no-implicit   # goal alignment off for this launch
```

To use implicit mode only on the launches where you ask for it, also run
`mnemom agent config set goal_mode off` (or set `goal_mode = "off"` in
`~/.mnemom/launcher.toml`), then pass `--implicit` on those launches. To opt
out, run `mnemom experimental disable implicit`. Until you opt in,
`--implicit` is refused with a pointer to `mnemom experimental enable implicit`,
and a saved `goal_mode = "implicit"` is ignored with the same pointer.

`--implicit` cannot be combined with `--goal`/`--requirement`/`--allow`/`--forbid`/`--goal-id`
— a sealed contract always wins on the gateway, so the launch refuses the
combination rather than silently ignore `--implicit`.

With the feature on, `mnemom agent goal` reads and steers the inferred goal of a
session:

```bash
mnemom agent goal show [ref]          # the live inferred goal (add --history for revisions)
mnemom agent goal pin [ref]           # stop new messages revising it (--off unpins)
mnemom agent goal reset [ref]         # clear it, or replace it with --statement "…"
```

What counts as your words, approvals, pin and reset, the
`mnemom agent goal show|pin|reset` commands and the known limits are on
[Implicit goal mode](/gateway/implicit-goal-mode).

In implicit mode the launcher tells the gateway which recent turns you typed and
which Claude Code inserted (a scheduled tick, a skill body, hook output), read
from Claude Code's own transcript. In terminal mode it runs a small local proxy
in front of the gateway to do this. Set `MNEMOM_AGENT_TURN_HEADER=0` to turn it
off.

`mnemom agent sessions` and `mnemom agent show` report a session's goal mode as
`ON` (sealed), `IMPLICIT`, or `OFF` — see [Sessions](#sessions-mnemom-agent-sessions--show)
below.

## Preflight: `mnemom agent doctor`

```bash
mnemom agent doctor
```

A read-only check with an actionable hint for anything not ready: your settings
file, the coding-agent CLI, your Anthropic key source, **gateway health** (a
`200` plus the `x-mnemom-verdict` header that proves governance is live), a
gateway that belongs to a different Mnemom deployment than the rest of the CLI,
your **Mnemom Agent access** for the active org, and the CLI's auto-update
status. It writes nothing, never reads
your key's value, and exits non-zero when the machine is not launch-ready, so a
script can gate on it.

## Account and µ balance

`mnemom agent` runs on µ and has **no free tier**. Before launching it checks the
µ balance on the org the agent lives in (by default your personal org). With no
µ, the launch stops with a top-up link; top up at
`https://mnemom.ai/settings/billing` and the balance updates the moment the
top-up completes. An accepted invitation credits your starter µ automatically.

## Defaults out of the box

| Default | Value | Override |
| --- | --- | --- |
| Gateway | `https://gateway.mnemom.ai` (the gateway the rest of the CLI uses) | `--gateway <url>`, `MNEMOM_AGENT_GATEWAY`, `config set gateway` |
| Launch shape | **Terminal** — a governed session in this terminal. | `config set launch` |
| Permissions | Claude Code's permission prompts are **off** (`--dangerously-skip-permissions`). See [Permission prompts](#permission-prompts) | `--no-yolo` (per launch) |
| Agent | a governed `agent-<you>` agent, claimed into your org before the first session | `--agent <slug>`, `config set agent` |
| Sign-in | Anthropic API key, unless you pick another option on first launch | `--auth`, `config set auth` |
| Key source | env → saved store → prompt | `config set key_source` |

A launch always uses one Mnemom deployment end to end: the gateway must belong to
the same deployment the CLI signs in to and reads your agents and sessions from.
A `--gateway` (or saved `gateway`) on a different deployment is refused at launch
and by `mnemom agent setup`, with the fix; a local gateway on `localhost` is
exempt.

## Saved settings: `mnemom agent config`

Configure the launcher once and stop retyping flags. Settings live in a
human-editable TOML file at `~/.mnemom/launcher.toml`. Your **Anthropic key is
never stored there**; it lives separately in `~/.mnemom/launcher.json` (mode
`0600`), so the file you open and share never carries a credential.

```bash
mnemom agent config list                 # show your current settings
mnemom agent config get model            # print one value
mnemom agent config set gateway https://gateway.mnemom.ai
mnemom agent config set launch terminal
mnemom agent config set guardrails.max_turns 200
mnemom agent config unset model          # remove one value
mnemom agent config edit                 # open ~/.mnemom/launcher.toml in $EDITOR
mnemom agent config path                 # print the file path
```

### Settable keys

| Key | Meaning |
| --- | --- |
| `gateway` | Gateway host (default `https://gateway.mnemom.ai`) |
| `model` | Model to launch (CLI alias or concrete id, e.g. `claude-sonnet-5`) |
| `agent` | Governed agent identity slug (`x-mnemom-agent`) |
| `effort` | Reasoning effort (`low`\|`medium`\|`high`\|`xhigh`\|`max`) |
| `cli` | Coding-agent CLI to launch (name or full path; default `claude`) |
| `launch` | Launch shape — `terminal` |
| `auth` | How Claude Code signs in to Anthropic: `api-key` (default), `subscription` or `console`. See [Sign-in options](/gateway/agent-sign-in) |
| `key_source` | Where to source the Anthropic key (`env`\|`store`\|`prompt`) |
| `goal_mode` | What a launch with no `--goal`/`--implicit`/`--no-implicit` does — `implicit` or `off`. Ignored until you opt in to the experimental `implicit` feature, so implicit mode is never on by default. After you opt in, an unset value means `implicit`; set `off` to use implicit mode only with `--implicit` |
| `context` | Context folding default — `true`/`false` (default `true`; also settable per-launch with `--context`/`--no-context`) |
| `context_profile` | How the gateway folds context — `balanced`, `aggressive`, `adaptive` or `off`; unset means the gateway's own default (also `--context-profile`, `MNEMOM_AGENT_CONTEXT_PROFILE`) |
| `compact_at` | Gateway compaction target — a token count from 50k to just under 1M (`200k` works), or `1m`/`off` for none (default: none). A target needs the experimental `compaction-intercept` feature (also `--compact-at`, `MNEMOM_COMPACT_AT`) |
| `guardrails.max_turns` | Contract guardrail: turn ceiling (positive integer) |
| `guardrails.budget_usd` | Contract guardrail: spend ceiling in USD (positive number) |
| `guardrails.stall_turns` | Contract guardrail: consecutive no-write turns (positive integer) |

### Precedence

Settings resolve highest-wins:

```
command-line flag  >  environment variable  >  ~/.mnemom/launcher.toml  >  built-in default
```

Guardrails saved in config apply only when a session has a goal, so a saved
ceiling never forces an unrequested contract.

An example `~/.mnemom/launcher.toml`:

```toml
gateway = "https://gateway.mnemom.ai"
model = "claude-sonnet-5"
agent = "agent-sam"
launch = "terminal"

[guardrails]
max_turns = 200
budget_usd = 25
```

## Your governed agent

Every `mnemom agent` session runs as a **claimed** agent. An unclaimed agent
belongs to no org and is billed to no one, so the launcher never starts a session
on one.

If you do not name an agent, the launcher uses `agent-<your handle>`, derived
from your Mnemom login. Before Claude Code starts, on every launch, it:

1. asks the gateway which agent it serves for this launch's credential and agent
   name. With an Anthropic API key, the answer is cached after the first launch.
   With a [Claude subscription sign-in](/gateway/agent-sign-in#claude-subscription-team-or-enterprise),
   the gateway is asked every time;
2. checks whether that agent is claimed. An agent that is already claimed is
   left where it is and never claimed again;
3. if it is not claimed, claims it into the org this launch bills: your active
   org (set with `mnemom org use`), else your personal org. Your active org
   setting is not changed. A newly claimed agent also gets its default cards.

The launcher prints one line naming the agent and saying whether it was already
claimed or has just been claimed, and into which org. Each agent it confirms as
claimed is recorded on this machine.

The launch stops, and Claude Code is not started, when the answer is definite:

- the agent for this credential and name belongs to another Mnemom account. Pick
  a name of your own with `--agent <name>`;
- the agent is not claimed and can't be claimed, for example because this launch
  has no org to claim it into. The message says what went wrong;
- the gateway does not support the subscription identity check yet. Launch with
  `--auth api-key` instead.

If Mnemom or the gateway can't be reached, or returns a temporary error, the
launcher retries. If it still can't get an answer, it launches on the agent this
machine last confirmed as claimed for the same credential, agent name and
gateway, and prints a warning saying so. If there is no such record, the launch
stops and asks you to try again. It never falls back to an agent it knows is
unclaimed.

This works the same way in a terminal, a script or CI. There is no prompt to
confirm the claim.

### Default cards

A newly claimed agent gets a default coding posture. Both cards are published
**off**, because alignment and protection analysis are billed: the alignment card
has `autonomy_mode` and `integrity_mode` set to `off` and
`principal.relationship: delegated_authority`; the protection card has
`mode: off`, with thresholds `0.60 / 0.80 / 0.95` and all four screen surfaces
declared so it is ready when you turn it on. Turn them on with
[`mnemom card`](/gateway/cli#card-commands) and
[`mnemom protection`](/gateway/cli#protection-commands). The goal contract does
the nudging.

```bash
mnemom agent setup                  # check (and if needed claim) the agent and refresh its cards; no launch
mnemom agent my-session --setup     # the same, then launch
mnemom agent my-session --no-setup  # skip the default-card writes for this launch
```

`--no-setup` only skips the card writes. The agent is still checked and, if
needed, claimed. `mnemom agent setup` uses an Anthropic API key. Bring your own
agent any time with `--agent <slug>`.

### Managing agents

The agent-management verbs live under the same namespace:

```bash
mnemom agent list [--org <slug|id>] [--all]           # agents in your active org (--all: every org)
mnemom agent claim <id-or-name> --key <key> [--org <slug>]
mnemom agent move <id-or-name> --to <slug|id>
```

## Sessions: `mnemom agent sessions` / `show`

Every real launch is appended to a local ledger, `~/.mnemom/sessions.jsonl`.
Entries older than 30 days are removed at the next launch; change that with
`mnemom config set sessions.retention_days <days>` (or
`MNEMOM_SESSIONS_RETENTION_DAYS`).

```bash
mnemom agent sessions          # the last 20 launches, newest first
mnemom agent sessions --all    # every launch
mnemom agent sessions --json
```

```bash
mnemom agent show              # the newest session
mnemom agent show fix-auth     # by session name (newest match wins)
mnemom agent show a1b2c3d4     # by a unique conversation-id prefix
mnemom agent show --json
```

`show` merges the local launch record with the gateway's **live** goal state for
that conversation — the sealed contract (if any), the latest verdict, and
guardrail gauges (`turns 3/10`, etc., flagged when a ceiling was crossed) — so
you can check on a session after the fact without re-reading your terminal
scrollback. It also prints the command that resumes the session through
`mnemom agent` (see [Resume a session](#resume-a-session)). Each row's `Goal` column, and `show`'s goal-mode field, read `ON`
(sealed contract), `IMPLICIT`, or `OFF`. For an implicit-mode session, `show`
also prints the statement the gateway inferred.

## Contracts and guardrails

A goal (`--goal`) seals a contract on the first turn; add
requirements, path rules and guardrail ceilings on the command line. Passing any
contract flag makes `--goal` required.

```bash
mnemom agent refactor-auth \
  --goal "Refactor the auth module without changing its public API" \
  --requirement "All existing tests keep passing" \
  --allow "src/auth/**" \
  --forbid "**/*.env" \
  --max-turns 200 --budget 25
```

The CLI prints the contract statement and its `sha256[0:16]` so you can confirm
what was sealed. The gateway echoes the full hash back on every response as
`x-mnemom-contract-hash`.

### Limits

| What | Limit | If exceeded |
| --- | --- | --- |
| Goal statement | 4,000 characters | first turn rejected with `400` (`statement_too_long`) |
| Whole contract (statement + requirements + paths + ceilings, as canonical JSON) | 8,192 bytes | first turn rejected with `400` (`contract_too_large`) |
| `--max-turns`, `--stall` | any positive whole number | the CLI refuses the flag before launching |
| `--budget` | any positive USD amount (decimals allowed) | the CLI refuses the flag before launching |
| Requirements, `--allow`, `--forbid` | no count limit; only the 8,192-byte total applies | — |

The contract is sealed on the **first turn** of a session. A later request that
sends a different or invalid contract header is ignored outright and the sealed
contract keeps governing, so a client hiccup mid-session never kills a governed
session — the only way a live seal's terms change is the owner update path
below.

### Seal lifetime

A seal lives for 24 hours since it was last touched by an active request on
that conversation — each request slides the window forward, so a session you
keep using never lapses on its own. If the session goes quiet for a full 24
hours, the seal lapses: `mnemom agent show` reports it as `EXPIRED`, and the
next request that carries a goal seals a brand-new contract (version 1 again,
fresh guardrail and judge counters) rather than reviving the old one.

### Updating a sealed contract

The agent itself can never change its own sealed contract — not by asking for
it, and not by writing something the fence would otherwise allow. The one way a
live seal's requirements, path rules, mode or ceilings change after the first
turn is an explicit update made through the contract's owner-credentialed
update path, never inferred from anything said in the conversation.

An update writes a new version of the same contract: the version number goes up
by one, and the record keeps a pointer to the hash it updated from. Guardrail
counters, the turn count and the judge's running state all carry over —
updating a contract changes its terms, not progress already made against them.

Two things to know before relying on an update:

- **Ceilings replace, they don't merge.** An update's turn/spend/stall ceilings
  replace the live contract's ceilings outright. To raise the turn ceiling while
  keeping the existing spend ceiling, resend both — an omitted ceiling means "no
  ceiling of this kind" on the new version, not "leave the old one in place".
- **Mode is the one field that carries over when omitted.** If the update
  doesn't name a mode, the session's current `nudge`/`enforce` mode is kept
  unchanged. Name a mode explicitly — including `nudge`, to downgrade an
  `enforce` session — and that value wins instead.

The update applies starting with the conversation's **next** request; a
request already in flight when the update lands was judged against the version
it started with. The session is told about the update once, on that next
request, as part of the governance text the gateway adds to the conversation.

### Ceilings: nudge vs enforce

Every sealed contract has a mode, `nudge` or `enforce` (default `nudge`, set
with `--mode`). The mode governs what happens when a guardrail ceiling — turns,
spend, or, when the contract sets one, wall-clock time — is crossed. `stall`
(consecutive no-write turns) is informational only in both modes; a crossed
stall ceiling is never grounds for a refusal.

**`nudge` (the default).** Guardrails **observe and nudge, never block**. Each
ceiling is checked once per turn; when one is crossed the gateway appends a
short `[mnemom guardrail]` line to your next message telling the agent which
ceiling it hit, and marks the crossing on the response headers and in your
traces. The session keeps running. A ceiling you leave unset falls back to the
cell's default for that guardrail, if the cell has one; otherwise it is simply
off.

**`enforce`.** A request that would run with a turn, spend or time ceiling
already crossed is refused outright, **before** the gateway calls the model, so
an enforce refusal never costs a model call. The response is an HTTP `429`
with `error.code: "goal_contract_enforce_refused"`, naming which ceiling(s) are
over along with their current value and limit. The session cannot raise its own
ceiling; only the contract's owner can, through the update path above — and
because the check compares the live counters against the live ceilings fresh on
every request, rather than remembering that a ceiling once fired, raising the
ceiling unblocks the very next request with no other action needed.

### Fence coverage

`--allow`/`--forbid` path rules are enforced mechanically, not only by the
judge's reading of the transcript: the gateway classifies every tool call and
shell command the agent runs as a read, a write or an exec, and checks a
write's target path against your fences.

- `Edit`, `Write`, `MultiEdit` and `NotebookEdit` are always writes.
  `Read`, `Grep`, `Glob`, `LS`, `WebFetch`, `WebSearch` and `TodoRead` are
  always reads and are never checked against a fence.
- Inside a `Bash` call, the gateway parses shell redirections and common
  write-shaped commands (copy, move, make-directory and similar) out of the
  command text — including across a pipeline — to find the file(s) a command
  writes, and checks each one that resolves to a concrete path.
- A write whose target the gateway can't resolve to a concrete path at parse
  time — one built from a shell variable, a command substitution, or similar —
  is not treated as a violation by default. The gateway works through a
  resolution ladder (the value as written, variables set earlier in the
  session, then evidence in the tool's own result) before giving up on it; a
  target still open after that ladder sets no automatic verdict. The judge
  decides from the full turn, and the step's fence-check line in your traces
  names the target as unresolved rather than silently passing over it.
- A resolved write that lands outside every allowed path, or under a forbidden
  one, is always at least a `violation` verdict. The mechanical check can only
  raise the judge's verdict on a fenced write, never lower it, and on its own it
  never blocks the request either way — see [Ceilings](#ceilings-nudge-vs-enforce)
  above for what does.

### Final-turn judging

Every assistant turn in a sealed session is graded against the contract. Most
turns are judged from the request that follows them — the gateway grades the
previous turn when it sees the next one. That leaves a session's very last
turn with no later request to grade it from, which matters most in a headless
run, where that last turn is often the exact push or pull-request step the
seal exists to govern. The gateway closes that gap itself: it judges the final
streamed turn directly, in the background, after your response has already
been sent, so a cut-off or aborted stream is still judged from what it did
produce and you see no added latency.

`mnemom agent show` reports any gap as `judging: unjudged <N>` (with
`· memoised <M>` alongside it for turns the judge's memo graded without storing
a fresh verdict). Under normal operation this reads `unjudged 0`; a nonzero
count means a turn's grading failed or is still in flight, not that judging is
turned off.

### Lead-directed sessions

`--lead-directed` adds one more fixed requirement to the sealed contract, on
top of whatever `--requirement` flags you pass: that this session may push its
own branches and open draft or ready pull requests, from a git worktree, but
never merge them. Pass it when a session is being run on someone else's
direction and that direction includes pushing branches or opening PRs on its
own — it turns "the lead said I could do this" into part of what the judge
grades the session against, instead of something asserted only in the
conversation.

```bash
mnemom agent ship-fix \
  --goal "Fix the flaky retry test" \
  --lead-directed \
  --requirement "Open the PR; do not merge it"
```

The requirement line itself reads:

> On the lead's direction, this session may push its own branches and open
> draft or ready pull requests, from a git worktree, never the primary
> checkout; it may not merge them.

Passing `--lead-directed` more than once on the same launch adds it only once
— the requirement never duplicates in the sealed statement.

## Context folding

Context folding summarizes older turns so a long session keeps fitting the
model's context window. It is **on by default**. Unless you choose a profile, the
gateway's own default profile applies.

```bash
mnemom agent long-session --no-context   # turn folding off for this launch
mnemom agent long-session --context      # force folding on (overrides launcher.toml/env)
mnemom agent config set context false    # make "off" the standing default
```

Precedence: `--context`/`--no-context` wins, else `MNEMOM_AGENT_CONTEXT`
(`0`/`false`/`off`/`no` turn it off), else `config set context`, else on.

### Context profiles

`--context-profile` picks how the gateway folds the session. With no profile set
anywhere, nothing is sent and the gateway's default applies.

| Profile | Behaviour |
| --- | --- |
| `balanced` | Keeps more of the earlier work verbatim and folds later — for long sessions that revisit earlier files and decisions. |
| `aggressive` | Folds earlier and keeps a tighter working set — for cost-sensitive sessions and short, focused tasks. |
| `adaptive` | Sizes the fold to the conversation: no fold below 200k tokens, `aggressive` from 200k to 1M, `balanced` above. |
| `off` | No gateway folding; compaction is left to the coding agent. Same as `--no-context`. |

```bash
mnemom agent long-session --context-profile aggressive
mnemom agent config set context_profile aggressive   # standing default
```

Precedence: `--no-context` (always `off`; combining it with any other
`--context-profile` is refused), else `--context-profile`, else the profile of
the session being resumed (with `--continue` or `--resume <session-id>`), else `MNEMOM_AGENT_CONTEXT_PROFILE` / `config set
context_profile`, else `off` when folding is turned off by `context = false` or
`MNEMOM_AGENT_CONTEXT`, else the gateway's default.

## How Claude Code signs in

Claude Code can sign in to Anthropic three ways under `mnemom agent`: an
Anthropic API key (the default), your Claude Team or Enterprise subscription, or
the API key your Anthropic Console login created. Your first launch in a
terminal asks which one when there is a choice, and saves the answer.
[Sign-in options](/gateway/agent-sign-in) covers each one, where the API key is
looked up, and what you see when something is missing.

## Flags

| Flag | Meaning |
| --- | --- |
| `--invite <token>` | Redeem a Mnemom Agent invitation, then launch if a session name is given |
| `--auth <mode>` | How Claude Code signs in: `api-key`, `subscription` or `console` — see [Sign-in options](/gateway/agent-sign-in) |
| `--goal`, `--requirement`, `--allow`, `--forbid`, `--goal-id` | Contract fields (`--goal` required if any are given) |
| `--implicit` / `--no-implicit` | Turn implicit goal alignment on/off for this launch (`--implicit` needs the opt-in experimental `implicit` feature; not combinable with the contract fields above) |
| `--max-turns`, `--budget`, `--stall` | Guardrail ceilings |
| `--mode <nudge\|enforce>` | Contract mode (a contract field — requires `--goal`); default `nudge`. See [Ceilings: nudge vs enforce](#ceilings-nudge-vs-enforce) |
| `--lead-directed` | Add the fixed lead-directed push/PR requirement (a contract field — requires `--goal`). See [Lead-directed sessions](#lead-directed-sessions) |
| `--agent <slug>` | Governed identity (default `agent-<you>`). Claimed before launch either way |
| `--cli <name\|path>` | Coding-agent CLI to launch (default `claude`) |
| `--gateway <url>` | Gateway host override |
| `--model <alias\|id>`, `--effort <level>` | Model + reasoning effort |
| `--trim-mcp` | Launch with no MCP servers |
| `--no-yolo` | Keep Claude Code's permission prompts: do not pass `--dangerously-skip-permissions` |
| `--context` / `--no-context` | Force context folding on/off for this launch (on by default) |
| `--context-profile <profile>` | `balanced`, `aggressive`, `adaptive` or `off` — see [Context profiles](#context-profiles) |
| `--compact-at <n\|200k\|1m\|off>` | Gateway compaction target for this session, from 50k to just under 1M; `1m` or `off` means none. A target needs the experimental `compaction-intercept` feature |
| `--conversation-id <id>` | Conversation id to send (default: generated) |
| `--no-context-hint` | Do not seed Claude Code's context-hint feature flag |
| `--no-context-handoff`, `--no-compaction-intercept` | Keep that experimental feature off for this launch, even when your settings turn it on |
| `--setup` / `--no-setup` | Re-check the agent and refresh its default cards / skip the card writes. The agent is claimed either way — see [Your governed agent](#your-governed-agent) |
| `--dry-run` | Print the resolved launch plan and exit |
| `--first-run` | Show the [first-run savings screen](/gateway/agent-savings) again, then exit |

Anything after `--` is passed straight through to the coding-agent CLI.

Flags of experimental features (`--implicit`, `--slack`, `--context-handoff`,
`--compaction-intercept`) are hidden from `--help` until you turn the feature on
with [`mnemom experimental enable`](/gateway/cli#experimental-features-mnemom-experimental).
