# Sovereign-agent composition

[Governance signals](/concepts/governance-signals) are operator-actionable observations. The Mnemom platform surfaces them to operators (UI, webhook, REST) — it **never** injects them into agent prompts.

But some applications run *sovereign-CTO-shaped* agents: agents who legitimately have authority and tools to act on fleet-level signals. The canonical example is Wintermute on Polis — a fleet orchestrator with reorganization tools who genuinely benefits from knowing the fleet has just `cluster_partition`'d.

For those agents, the application — not the platform — owns the decision to render a governance signal into the agent's prompt at request-prep time.

This guide documents the pattern.

## When to use this pattern

✅ **Yes** — your agent has fleet-management tools, can act on team-shaped signals, and operator culture treats it as a CISO-equivalent for its own fleet.

❌ **No** — your agent is one of many in a team, has no team-management capability, and would be told "Recalibrate fleet alignment before the next response" with no actionable lever. That's the architectural mis-layering [ADR-048](https://github.com/mnemom/scale/blob/main/decisions/ADR-048-governance-signals-layering.md) corrected; auto-injecting is exactly what it ruled out.

If you're unsure, the default is **no**. Operators will see the signal in the dashboard regardless.

## Architecture

```
                                  ┌─ Mnemom UI dashboard
Mnemom platform ───────────────── ├─ governance.signal.fired webhook
  detector ──> governance_signal  ├─ GET /v1/agents/:id/governance/signals
                                  └─ (other operator surfaces)
                                              │
                                              │  Application (e.g., Polis)
                                              │  decides per-agent if sovereign
                                              ▼
                                       Sovereign agent's
                                          system prompt
                                       (rendered as a
                                        <governance_signals>
                                        block at prep time)
```

The platform is **only** the operator side. The dotted line from "operator surfaces" into "sovereign agent's system prompt" is application code that you own.

## Pattern (TypeScript)

The [`@mnemom/agent-alignment-protocol@1.1.0+`](https://www.npmjs.com/package/@mnemom/agent-alignment-protocol) package ships a worked example at [`examples/sovereign-agent-composer.ts`](https://github.com/mnemom/aap/blob/main/examples/sovereign-agent-composer.ts). The shape:

### 1. Application-side role config (NOT in the alignment card)

```typescript
interface AgentRoleConfig {
  agent_id: string;
  /** True for sovereign-CTO-shaped agents (e.g., Polis's Wintermute). */
  is_sovereign: boolean;
}
```

Critically: **this flag lives in your application's role config, not in the agent's [alignment card](/concepts/alignment-cards).** The alignment card is operator-authoritative governance content; the sovereignty decision is application policy. Keeping them separate preserves both surfaces' integrity.

### 2. Subscribe to the webhook (or poll the API)

```typescript
import {
  type GovernanceSignal,
  type GovernanceWebhookEnvelope,
} from "agent-alignment-protocol";

async function handleGovernanceWebhook(
  envelope: GovernanceWebhookEnvelope,
  cache: ApplicationCache,
  roleConfigs: Map<string, AgentRoleConfig>,
): Promise<void> {
  if (envelope.event !== "governance.signal.fired") return;
  const signal = envelope.payload;

  // Filter to signals affecting sovereign agents in your application.
  const sovereignAgents = signal.agent_ids.filter((id) => {
    const role = roleConfigs.get(id);
    return role?.is_sovereign === true;
  });

  if (sovereignAgents.length === 0) {
    // Non-sovereign agents: do NOT compose. Operator UI already shows
    // the signal; that's the right surface.
    return;
  }

  await Promise.all(
    sovereignAgents.map((agentId) => cache.putForAgent(agentId, envelope)),
  );
}
```

Pull-based alternative: `GET /v1/agents/:agent_id/governance/signals?status=open` at request-prep time.

### 3. Compose at request-prep time

```typescript
import { isFleetSignal, severityAtLeast } from "agent-alignment-protocol";

async function composeSovereignContext(
  agentId: string,
  roleConfig: AgentRoleConfig,
  fetchSignals: (id: string) => Promise<GovernanceSignal[]>,
): Promise<string | null> {
  if (!roleConfig.is_sovereign) return null;

  const signals = await fetchSignals(agentId);
  const material = signals.filter((s) => severityAtLeast(s.severity, "high"));
  if (material.length === 0) return null;

  const lines = ["<governance_signals>"];
  for (const sig of material) {
    if (isFleetSignal(sig)) {
      lines.push(
        `  [fleet:${sig.pattern_type}] team=${sig.team_id ?? "?"} ` +
          `affecting ${sig.agent_ids.length} agent(s); severity=${sig.severity}; id=${sig.id}`,
      );
    } else {
      lines.push(
        `  [${sig.source}:${sig.pattern_type}] severity=${sig.severity}; id=${sig.id}`,
      );
    }
  }
  lines.push("</governance_signals>");
  lines.push("");
  lines.push(
    "These are operator-level observations the platform surfaced via your sovereign role.",
  );
  lines.push(
    "You may reference them in your reasoning or use your fleet-orchestration tools to act on them.",
  );
  lines.push(
    "If any are no longer relevant, ack/dismiss via the operator dashboard rather than ignoring inline.",
  );
  return lines.join("\n");
}
```

Notice the agent's *own* declared system prompt comes first when assembling — the operator-side observations are supplementary context, not authoritative instruction:

```typescript
const govBlock = await composeSovereignContext(...);
const systemPrompt = govBlock
  ? `${baseSystemPrompt}\n\n${govBlock}`
  : baseSystemPrompt;
```

## Filter policy

The example filters to `severityAtLeast(s.severity, "high")`. Tune to your sovereign agent's role:

- A small fleet's CTO might see `warn+`.
- A large fleet's CTO might see `critical` only — they trust org admins to handle `high` and below from the operator UI.
- A research agent might see all severities for transparency, even when it can't act.

## Counter-example (read this first)

```typescript
// ❌ DO NOT do this for non-sovereign agents.
const signals = await fetchSignals(agent.id);
systemPrompt += `\n\n[Mnemom advisory: ${signals[0].source} flagged …]`;
```

A non-sovereign agent receiving "Recalibrate fleet alignment before the next response":

- has no team-management tool;
- has no acknowledgment surface;
- has no remediation it can perform from inside its LLM call.

The signal is real and important — but the recipient is wrong. Operator dashboard, webhook to ops Slack, on-call PagerDuty — those surfaces are where this signal lives. Auto-injecting it into the agent prompt is the [architectural mis-layering ADR-048 corrected](https://github.com/mnemom/scale/blob/main/decisions/ADR-048-governance-signals-layering.md#section-7).

## Acknowledgment from the agent's voice

A sovereign agent that *does* act on a signal should ack/resolve through the operator API, not by ignoring the signal:

```typescript
import { acknowledgeGovernanceSignal } from "your-mnemom-client";
// In a tool the sovereign agent invokes:
await acknowledgeGovernanceSignal(signalId, {
  action_taken: "Initiated team rebalance: see thread <link>.",
});
```

This goes through the same `acknowledged_actor_role` audit trail as a human operator's ack. The role recorded is the sovereign agent's effective role at action time (typically `service` or, if the agent runs under a service identity, the role associated with that identity).

## Polis worked example

The Polis V6 prompt assembler (per `polis/packages/core/src/emps/runtime/sections/governance_signals.py`) is the canonical reference implementation. Wintermute opts in via Polis's role config; non-sovereign Polis agents see nothing. This pattern ships as part of the broader Polis V6 work.
